Promotion: from personal facts to team rules

Date 9 Nov 2026Status Design, not builtBuilds on Layers and promotion spec

This spec says how to build promotion step by step. Each step can be built and tested on its own.

The ladder (personal rule at 1.75, team candidate at 3, admin approval), the weights and the "never demote automatically" rule follow the layers and promotion spec. This page covers how to build them.

1Architecture

Agent Memory holds what people know. Our backend and its SQLite file hold everything promotion needs to count and decide.

StepWhat happens
1A user captures a note in our app, or chats with Claude through the Agent Memory plugin. Either way it is stored in their personal scope, as today.
2On each run the promotion job lists the facts in every personal scope and keeps the ones it has not seen, as statements in SQLite: who holds it, what, and when. It also notices facts that were replaced since the last run.
3The job groups the new statements, recomputes scores and stages, and updates the review list. Only one run happens at a time.
4To group new statements, the job sends a small Claude model the statements and the existing topics from SQLite: first only the topics about the same subject, then all topics if none fits. The model picks a topic or says it is a new one.
5A team admin reviews candidates on Admin › Promotion. The API checks their grant first.
6On Approve, the backend writes one knowledge fact to the team scope.
7Ask reads personal, team and org scopes as before, so approved rules now appear in answers.

Every Agent Memory call uses a key limited to the scopes it needs. Users write only their personal scope. The job reads every personal scope and writes nothing to Agent Memory. Only the approval path writes to the team scope; no user, team admins included, can write there directly. No key is given the forget permission.

4What we store

Three SQLite tables, next to the existing grants table. Scores and stages are not stored; they are recomputed from statements each run, so a settings change takes effect on the next run.

TableOne row perMain fields
statementfact found in a personal scopeuser, scope, memory_ref (the fact's id in Agent Memory), source (chat or app, from the fact's source), text (the fact's summary), entity, key, value, said_at, group_id, stance (for, against), replaced_at, processed_at
fact_groupthing people make claims about, such as "Cobalt Ridge return window"label, subject (cleaned name used to filter topics), aliases (other subject names learned to mean the same thing), rule_entity, rule_key (the standard entity and key a team rule is written under), created_at
review_itemcandidate, flag or approved team rulekind (candidate, flag), group_id, value, score_when_listed, status, decided_by, decided_at, memory_ref (the fact written to the team scope), rule_id (for a flag, the rule it questions)

One review_item row follows a candidate through its life:

  • Candidate: open → active (approved, now a team rule) → closed (retired), or open → rejected, or open → dropped (score fell below the threshold).
  • Flag: one open flag per rule. It opens when the score against the rule reaches PROMOTION_FLAG_AT, then goes to kept or closed. Closing a flag also closes the rule it points to.
  • Closing a rule writes a closing value over it in the team scope that reads correctly in any answer, for example "no longer a team rule (closed by the team admin on 12 Nov)", labelled kind=closed. Agent Memory keeps the old value in its history with the date it ended. Our Ask modes also skip closed rules, using the ids in review_item.

Two things are worked out rather than stored:

  • Stages. A person's value is a personal rule while their own score is at least the threshold. The date it became one is the date of the statement that pushed it over.
  • Contributors to a rule. The statements for the approved value dated up to the approval.

The Promotion tab's last-run line is kept in the backend's memory, not stored. It shows blank after a restart until the next run.

5Deciding two people hold the same fact

This is the hardest part. Our tests stored the same term as promotional_discount_cap in one scope and max_promotional_discount in another, and dropped some values entirely.

5.1 Grouping: match against the topic list

Each fact group is a topic with a short label, such as "Cobalt Ridge return window", kept in SQLite. Only statements not yet processed are sent; topics are the choices the model picks from.

  1. Same subject first. The job cleans the statement's subject name (lower case, prefixes such as "organisation/" removed) and selects the topics with that subject or one of its aliases.
  2. Model picks. One small model call gets a batch of new statements and those topics. For each statement it answers with the matching topic, or "none of these".
  3. Full list if none fits. Statements with no match, or with a broad subject listed in PROMOTION_GENERIC_SUBJECTS, go to a second call with every topic label. Only then may the model say "new", with a short label and a standard entity and key for the new topic.
  4. Learn aliases. When the second call matches a statement to a topic under a different subject, for example "Cobalt Ridge return policy" to a "Cobalt Ridge" topic, that subject is saved as an alias. Next time those statements match in the first call.

In every case the model also returns the value in the form the topic already uses ("about two weeks" becomes "14 days").

Why not use Agent Memory's search for this. In check S1, its scores were fixed by rank (0.3800, 0.3739, 0.3679 for places 1 to 3 on every query), so it could not say "new topic", and it put the right topic first for only 4 of 11 statements. Each search also took 4 to 9 seconds. If topics ever number in the thousands, a search-based shortlist can be added in front of the model (check S2 showed how).

5.2 Agree or disagree

  • Same value as another statement in the group: counts for that value.
  • Different value: counts for its own value and against the others in the group. "30 days" and "60 days" are two values of one group.
  • The same person changes their value: a self-correction. Agent Memory replaces their old fact, the job sees it as replaced, and their newest value counts instead. Nothing is subtracted.
  • A fact is removed or replaced in Agent Memory: its statement gets replaced_at and stops counting.

Only facts count. A chat sentence that Agent Memory did not turn into a fact is not seen, because stored chat text cannot be listed. Facts drawn from Claude's own replies cannot be told apart from the user's, so they count for the scope's owner.

6Scoring

Each person's statements for one value add 1, 0.5, 0.25…; their statements against it subtract the same way. One person adds at most about 2.

  • Personal score: the holder's own statements only. Reaching PROMOTION_PERSONAL_RULE_AT makes it their personal rule.
  • Team score: the sum over all members of their "for" minus "against". Reaching PROMOTION_CANDIDATE_AT lists it for review. At 3 this always needs at least two people.
  • Counted from personal scopes only. Team and org scopes never add to a score.

1

Settings, tables and the scoring function

Add the settings and the three tables. Write scoring as a pure function: statements in, personal scores, team scores and stages out.

Done whenunit tests pass for the worked example above, self-correction, opposing values and the test profile.

2

The common team scope

Create the team scope and give every member read access from Admin › Access. Mark the chosen team admins with the team-admin role. Nobody gets write access; Capture does not offer the team scope.

Done whenevery member's Ask reads the team scope and no user key can write to it.

3

Read new and changed facts from personal scopes

At the start of each run, list the facts in every personal scope. Add a statement for each fact id not seen before, skipping links added by background jobs. Mark statements whose fact was replaced or removed.

Done whena fact saved through Claude chat with the plugin, and one saved in Capture, both appear as statements for the right person, and correcting one marks the old statement replaced.

4

The promotion job: grouping

Process statements not yet handled, in batches: match them to topics (same subject first, full list if none fits), save new topics and learned aliases, and decide agree or disagree. Runs every PROMOTION_JOB_EVERY and from Run now. A lock keeps it to one run at a time; Run now during a run shows "already running".

Done whenthe conflict-test notes (30 / 45 / 60 days) land in one group with three values, and unrelated notes start their own groups.

5

The promotion job: scores, stages and the review list

After grouping, recompute scores and stages, open candidates at the threshold and mark dropped ones. Open a flag when the score against an active team rule reaches PROMOTION_FLAG_AT, one per rule.

Done whenreplaying the worked example with test users gives the same scores and list changes.

6

Admin › Promotion tab and approval

Build the Promotion sub-tab shown in section 7 and the backend calls behind it. Approve writes the team rule.

Done whenan approved rule appears in the team scope, Ask finds it, and the decision shows who approved it and when.

7

End-to-end run

With at least three test users and the test profile: save agreeing and conflicting facts, some through Claude chat with the plugin and some in Capture. Run the job, approve a candidate, then ask the question in each Ask mode. Close the rule and ask again.

Also check that the team scope holds only approved rules after background elaboration has had time to run (check S7).

Done whena fact goes from three personal scopes to one team rule in one sitting, and the run is written up.
